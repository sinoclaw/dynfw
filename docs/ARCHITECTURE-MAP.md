### 4.2b 核心结论：O(T) 压缩 与 O(T²) 精确 统计等价（2026-09-12，8 seed）
**口径**：W=64，D=128 nh=16 L=2 mm=64 steps=1，20ep，corpus_en，共享教师 logits，全部 `read_mode=raw`。

| 架构 | n | 中位 | 均值 | std | 范围 |
|---|---|---|---|---|---|
| ~~v5 `la_cycle`（精确 O(T²)）~~ 🪦 **本体已删（2026-09-12，理由见 §7）** | 8 | 80.28 | **80.27** | **1.78** | 77.55 ~ 83.15 |
| **v6 `fw_cycle`**（压缩 O(T)） | 8 | 82.47 | **82.03** | 3.62 | 75.50 ~ 87.42 |
| **v6.6 `gdn_cycle`**（门控 O(T)） | 8 | 81.40 | 82.13 | 6.06 | 75.48 ~ 94.82 |

Welch t-test（双尾）：
| 比较 | Δ均值 | SE | t | df | p | 判定 |
|---|---|---|---|---|---|---|
| v5 vs v6 | −1.75 | 1.43 | −1.23 | 10.2 | **0.246** | 不显著 |
| v5 vs v6.6 | −1.86 | 2.23 | −0.83 | 8.2 | **0.429** | 不显著 |
| v6 vs v6.6 | −0.11 | 2.50 | −0.04 | 11.4 | **0.967** | 不显著 |

**结论（须按此表述，不得夸大）**：
1. **在 8 seed 本口径下，压缩架构（O(T)）与精确架构（O(T²)）的能力差异不具统计显著性**
   （点估计 v5 优 1.75 分，p=0.246）。⇒ 「把 O(T²) 换成 O(T) 的能力代价」在统计上**未被检出**。
2. **门控（v6.6）在短 T 无收益**（p=0.967）⇒ 「门控=删记忆伤能力」的旧判断作废（那是 softmax 口径下的假象）。
   门控的真实价值只在**长 T 控范数**（‖M‖ T=8192: 46,148 → 4,647），本口径（T=256）测不出，**待长 T 验证**。
3. **检验力说明**：Δ=1.75、SE=1.43 ⇒ 要达 p<0.05 需每边约 20 seed。当前只能声称「未检出显著差异」，
   不能声称「完全等价」或「v6 更优」。
4. v5 方差最小（std 1.78）⇒ **训练稳定性**上 v5 仍占优（这是压缩路线尚存的真实短板）。

**PPL 说明**：三架构 `ppl_est` 字段均为 10686474581524（vocab=151936 导致数值溢出），**不具可比性**，
一律以 `final_loss`（KL 口径）为准。

#### ⚠️ 机制（2026-09-12 定位，跨实例可复现）
**`torch.compile` 在首次调用时才真正编译。若编译那一刻 eager 路径已经跑过（cuBLAS/cuDNN 库级计划已建立），
inductor 生成的代码快 1.87×；否则生成保守代码。**
- 证据矩阵（T=1024，各变体独立进程）：直接 compile **16.14ms** / 同实例先 eager 5 步 **8.65ms** /
  **另一个 opt5 实例**先 eager 5 步 **8.64ms**（跨实例有效 ⇒ 进程级库状态）/ 先用 TF 跑 5 步 **14.90ms**（无效）。
- **编译之后的 warmup 步骤无效**：compile 后再插 eager 预热仍是 15.6ms，长跑 60 步稳定在 14~16ms。
- GPU 预热不是原因：30 步预热后 15.92/72.94/140.20/277.29，与冷启动逐位相同。
- 这解释了此前"混合进程 0.88~1.83×、单进程 0.52~0.99×"的 1.8× 之谜：**混跑时前面的形态替后面做了 eager 预热**。

#### 结论（必须按此表述）
1. **含"编译前 warmup"（业界标准做法）**：T≥16K 反超（**1.27× / 1.85×**），T≤8K 打平（0.96×）
   ⇒ **O(T) 卖点在长上下文成立，交叉点 ≈ T=8~10K**。
2. **不含 warmup（保守口径）**：全档 ≤1.0×（0.52~0.99×）⇒ 卖点不成立。
3. **对外报数必须同时声明口径**（是否含编译前 warmup），否则数字不可比。
4. 评测入口**必须内置编译前 warmup**，否则会系统性低报 1.87×。
5. 修正旧账：「v6 慢 TF 3.2×」= 未优化实现 vs SDPA 融合核，口径不对等，作废。
6. `raw` vs `softmax` 速度无差异（1.85× vs 1.80×）⇒ **raw 是纯赚**（能力 +8.5 分、速度不亏）。

**J1 验收**：参数逐位相同（45,187,072）、logits maxdiff ≤ 8.35e-07、因果探针 maxdiff=0。

#### B 线（TileLang）判定：❌ 当前配置下不划算
- 孤立段（B=2 nh=8 w=256 单段）：TileLang **15.44ms** vs compile 手写 bmm **105.78ms** ⇒ **6.85×**（已排除 v 广播口径误差）。
- **端到端**（同口径）：TileLang **328.25ms** vs `a_comp` **150.19ms** @32K ⇒ **0.457×（慢 2.2×）**；
  单进程复测 328.25 vs 277.37（a_comp 无预热）仍慢 1.18×。
- 根因：kernel 配置（block_M=block_N=64）在端到端的 2048×batch 网格下变成 8192 个小 block（每块仅 ~6.3M MACs），
  调度开销主导；打不过深度调优的 cuBLAS。
- **按跑前锁死判据（端到端 ≥1.15× 才值得继续）：不划算，如实记录。**
  若重启该线，第一步应扫 kernel 配置（block 尺寸 / num_stages / threads），而非改数学。
- J1'（接进模型后）：参数全等、logits 与 `a_comp` **逐位一致（0.000e+00）**、因果探针全 0 ⇒ 实现本身正确。

| 「V6_BREAKTHROUGH：v6 能力 + O(T) 双达标」 | 能力那半是 D1 泄漏 artifact（见上） |

## 6. 铁律（每次对轰前逐条核）

0. **分块架构报分前必须验证 chunk 数 = T/W > 1**：W = block 时整层只有 1 个 chunk，跨块记忆被
   **静默关闭**，架构退化成「仅块内自注意」，读数与架构能力无关（v6 的 354 全由此产生）。
   各架构对比必须用**同一个 W**，否则是脏评测。

1. 速度对轰：**双方必须同优化等级**，且优化必须**真的接进评测入口**。
2. 不同尺子（配置/口径）的数字**不可互比**，引用时必须写配置。
3. KL = 模仿分，不是能力分；能力分须真实 checkpoint + 标准评测。
4. 报数必须附：配置、预算、seed、优化形态、**因果性验收状态**。
5. **缺陷无存量豁免**：底层版本带缺陷，其历史读数一律作废重测。
6. 修 bug 必须做**不变量回归**（如 D2 修复后 raw 路径 logits 逐位不变），证明未波及有效读数。

**口径**：T=8192 / 20 块（=163,840 token 的连续文本流）/ 1000 step / 3 seed / 同教师 Qwen3-0.6B /

## 4.2e v6.7 = v6.6 门控段换 FLA chunked 内核 —— 能力/速度双料第一（2026-09-13）

### 动机
v6.6 的门控 `M = α·M + k⊗v` 破坏了 v6 的"纯累加"结构 ⇒ cumsum 前缀和不再可用 ⇒ 跨块记忆段
退化为 `T/W` 次串行循环（T=8192/W=64 = 128 次）。**实测该段正是 v6.6 慢 2.9× 的根因**
（隔离 bench：同形状下顺序循环 178.1ms vs FLA 14.6ms）。

### 实现（`dynfw/models/fused_fw_gdn_fla.py`，`GDNFastAttnFLA`）
- **数学依据**：v6.6 的 `agg = 块内 raw 注意 + q_t@M_prev` = **带衰减的全局线性注意 = GLA**
- 用 `fla.ops.simple_gla.fused_chunk_simple_gla`（**head-wise 标量门控**，正是我们的形式）。
  **不是 `gated_delta_rule`** —— 那多了 `M·k` 预测残差项，正是 v6.5 崩掉的原因
- 参数量与 v6.6 **完全一致**（45,188,098），可权重互转
- **`gate_mode='block'` 可精确复现 v6.6**：块内 `g=0`（不衰减）+ 块首 `g=log α_blk`
  ⟹ `S_块末 = α_blk·S_块初 + Σ_j k_j⊗v_j`，实测同 seed 小配置 final_loss 差 **5.6e-6**（实质逐位一致）

### 关键提速：FLA 的 kernel 在 fp32 下反向慢 11×（先测后改，两条独立证据）
- **op profile**：FLA kernel 系占步长 **70.6%**；内存搬运仅 2.7% ⇒ **排除** permute/fp32 强转嫌疑
- **dtype 微基**（同形状 T=8192/H=16/K=N512/V=D128）：
  | dtype | 前向 | fwd+bwd |
  |---|---|---|
  | fp32 | 5.00ms | 162.38ms |
  | bf16 | 2.23ms | **14.70ms** |
  ⇒ **fp32 训练慢 11.05×**（前向仅差 2.24×）
- **处置**：FLA 段走 bf16，其余保持 fp32。**这是修口径不是取巧** —— 对照组 opt5 本身即
  `strict_bf16=True`，此前"fp32 的 FLA"比"bf16 的 opt5"本就不公平
- 效果：**fwd+bwd 377.5ms → 68.7ms（快 5.5×）**

### 战绩（T=8192 / 20块 / 50ep=1000step / 3 seed；判据跑前锁死）
| 架构 | 中位 | 均值 | std | wall | 纯计算 fwd+bwd | 显存 |
|---|---|---|---|---|---|---|
| **v6.7 bf16 FLA** | **5738.0** | 5750.6 | **21.3** | 536.1s | **68.7ms** | **5.13GiB** |
| v6.7 fp32 FLA（已作废） | 5830.7 | 5804.3 | 61.3 | 897.0s | 377.5ms | 5.75GiB |
| v6.6 gdn | 7142.6 | 7105.2 | 80.4 | 1548.4s | 994.3ms | 5.56GiB |
| v6 fw_cycle(opt5) | 8260.9 | 8316.1 | 92.1 | 537.8s | 91.2ms | 5.99GiB |
| tf SDPA | 19734.9 | 19713.1 | 43.6 | 561.9s | — | — |

**Welch t 检验**（`stat_util.py` 纯 stdlib；**注意其返回顺序是 `(t, df, p)`**）：
```
v6.7 vs v6   : t=-38.39  p=0.00036  ★ 改善 30.5%
v6.7 vs v6.6 : t=-23.03  p=0.00095  ★ 改善 19.7%
```

**速度三口径**：纯计算 **68.7ms**（比 v6+opt5 的 91.2ms 快 1.33×）；实验 wall 536.1s ≈ v6 的 537.8s。
⚠️ **wall 含 mmap 读 47GB 教师 logits 的 IO（~537s）⇒ 报速度必须用纯计算口径**（此坑已犯过一次，
见 §4.2c 收口实验 v6 与 tf 的 wall 都卡在 547s）。

### 诚实标注（不可省）
1. **收敛判据不通过**：末 200 step v6.7 降 24.5% / v6.6 降 25.4% / v6 降 26.0%（tf 仅 4.9%）
   ⇒ **排名是趋势，非终局**
2. **v6.7 相对 v6.6 同时改变两个变量**（①实现方式 ②门控粒度 块级→逐token）；
   单变量归因见 `final_lt8192_flablock_*`（`--fla-gate block`，已验证可精确复现 v6.6）
3. **`o` 读出差一个 α_t 因子**（FLA = `α_t·(q_t@S_{t-1})`，v6.6 = `q_t@M_prev`）⇒ **不声称位级等价**

## 4.2f 单变量归因：v6.7 的 +19.7% 全部来自「门控粒度」，速度 2.63× 全部来自「实现方式」（2026-09-13）

### 背景
v6.7 相对 v6.6 同时动了两件事（①实现方式 顺序循环→FLA 并行 ②门控粒度 块级→逐token），
此前只能报「合成效应」。本臂用 `--fla-gate block` 把门控语义还原成 v6.6（前已小配置验证精确复现），
于是得到三个臂的干净对照。

### 结果（T=8192 / 20块 / 1000step / 3 seed）
| 臂 | 门控粒度 | 实现 | 中位 | 均值 | std | wall |
|---|---|---|---|---|---|---|
| **A** | 块级 | FLA | 7140.0 | 7106.2 | 72.9 | **589.4s** |
| **B**（v6.6） | 块级 | 手写顺序循环 | 7142.6 | 7105.2 | 80.4 | 1548.4s |
| **C**（v6.7 主线） | **逐 token** | FLA | **5738.0** | 5750.6 | **21.3** | 536.1s |

### 单变量拆解（Welch，`stat_util.py` 返回 `(t, df, p)`）
```
A vs B（纯实现方式差异，同块级语义）: t=  0.01  df=3.96  p=0.990763  不显著   改善  0.0%
C vs A（纯门控粒度差异，同 FLA 实现）: t=-25.26  df=2.34  p=0.000664  ★显著    改善 19.6%
C vs B（合成效应）                  : t=-23.03  df=2.28  p=0.000950  ★显著    改善 19.7%
```

### 结论（两个变量正交，各自贡献明确）
```
能力 +19.7%  ←  100% 来自「门控粒度」（块级 → 逐 token）；实现方式贡献 0.0%（p=0.99）
速度 2.63×   ←  100% 来自「实现方式」（顺序循环 → FLA 并行，同块级语义下 1548s → 589s）
```
**意义**：
1. **FLA 换来的不是能力，是「负担得起逐 token 门控」的算力**——而能力增益恰恰来自逐 token 门控本身；
2. **「块级门控」当初是省算力的妥协**（顺序循环下逐 token 太贵），不是设计选择 ⇒ v6.7 把它解锁了；
3. **实现方式的等价性再次被证实**（p=0.99，与 §4.2e 小配置的 5.6e-6 差一致）⇒ 归因可信。

### 附带的中间结论修正（重要）
- **「门控伤能力」彻底作废**：该结论只成立于**块级门控 + 短 T**。逐 token 门控在长 T 下**净增益 +19.6%**。
  ⇒ 台账与技能里凡写「门控衰减=遗忘、伤能力」的地方均已更正（见 §4.2e 与技能主文件）。
- **v6.7 的 std 最小（21.3 vs 72.9 / 80.4）** ⇒ 逐 token 门控不仅更强，也更稳。
