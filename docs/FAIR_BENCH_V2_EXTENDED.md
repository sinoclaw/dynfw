# FAIR_BENCH_V2 (extended) —— 补基准覆盖：batch × seq 矩阵

> 脚本：`experiments/v0_0_1_baseline/fair_bench_v2_extended.py` · 数据：`results/v0.0.1/fair_bench_v2_extended.json` · CPU 口径 · 复用 v0.0.1 ~400K 参数匹配模型（TF_sdpa / FusedFW+FFN）
> v0.0.1 只测了 prefill batch=8、T 到 4096；本扩展把 **batch ∈ {1,8,32}** 与 **T ∈ {256,1024,4096,8192}** 两个轴钉全（wall-clock）。

## decode @ batch1（自回归逐 token）
TF **0.75 ms/tok**，FW **0.36 ms/tok** → FW/TF = **0.47**（FW ~2.1x 快）。

## 解读
1. **O(T) 缩放跨 batch 成立**：无论 batch 1/8/32，**FW/TF 都随 T 单调下降**（短序 ~1.0 慢 → 长序 0.18-0.36 快）——**无自注意力的 O(T) 线性优势在长上下文放大**，与 v0.0.1 结论一致，且**不依赖 batch**（batch 只是常数上移，不改趋势）。
2. **短序（T=256）FW 略慢**（1.0-1.1x）——O(T) 红利在极短序列未显现，FW 的索引/固定开销占比重。**长上下文（≥1K）才是 FW 主场**。
3. **batch 增大整体降低效率**（两架构都更慢），但 **FW/TF 比值基本稳定**（同一 T 下 batch 1↔32 的趋势一致）→ batch 不是 FW 优势的敏感变量。
4. **decode 仍 FW 便宜 ~2.1x**（v0.0.1 同口径），是部署口径的硬资产。

## 边界（诚实）
- 仅 CPU 口径；**GPU 列（FlashAttention 基线）本地无卡，标"待补"**，不假装测过。
- 定位于小型 char-LM；长上下文质量（真实困惑度/下游任务）仍未评估（roadmap 下一阶段）。
